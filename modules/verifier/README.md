# Physics Lab Checker

Стартовый модуль проверяющего агента для мультиагентной системы на LangGraph.

## Возможности

- входная проверка до Диспетчера;
- маркировка пользовательского/OCR/документного текста как недоверенных данных;
- поиск типичных признаков prompt injection (эвристика, не полноценная гарантия безопасности);
- LLM-проверка утверждений по `sources`;
- программная сверка чисел по `numbers`;
- проверка размерностей через Pint, если размерность/единица задана;
- проверка вопроса и эталонного ответа Экзаменатора;
- вердикты `pass`, `revise`, `refuse`;
- максимум одна повторная попытка исправления;
- журнал проверок в общем State.

## Установка

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

LLM-проверки требуют `OPENAI_API_KEY`. Без ключа Source Judge и Examiner Validator возвращают `needs_review`,
а не притворяются, что проверка пройдена.

## Контракт State

`state.py` содержит TypedDict общего состояния. Команда должна согласовать его поля с остальными агентами.
Проверяющий не должен заменять весь State: узлы возвращают только обновляемые ключи.

Основные поля, которые должны заполнять другие агенты:

- `student_message`: исходное сообщение студента;
- `context`: словарь с контекстом лабораторной;
- `agent_name`: имя агента, чей результат проверяется;
- `agent_response`: текст ответа агента;
- `sources`: список источников `{"id": "...", "text": "...", "origin": "..."}`;
- `numbers`: словарь численных результатов;
- `examiner_payload`: объект `{"question": "...", "expected_answer": "..."}` для Экзаменатора.

Рекомендуемый формат `numbers`:

```json
{
  "current": {
    "value": 2.0,
    "unit": "ampere",
    "display_name": "сила тока",
    "tolerance_abs": 0.001,
    "tolerance_rel": 0.0001
  }
}
```

В `agent_response` для надёжного сопоставления рекомендуется явно указывать название величины и единицу:
«Сила тока равна 2 А».

## Интеграция в основной LangGraph

1. Перед узлом Диспетчера вызовите `input_guard_node`.
2. После каждого агента вызовите `validate_agent_output_node`.
3. Если `verdict == "revise"`, передайте `feedback` исходному агенту и увеличьте `retry_count`.
4. После повторной генерации снова вызовите `validate_agent_output_node`.
5. Если повторная проверка не пройдена, не отправляйте ответ студенту.
6. При `verdict == "refuse"` завершите ветку безопасным отказом.

См. `integration_example.py`.

## Важные ограничения начальной версии

- Regex-фильтр обнаруживает только типичные формулировки атак. Это не полноценный классификатор и не гарантия защиты.
- Маркировка `<untrusted_data>` сама по себе не защищает от prompt injection. Все последующие LLM должны получать явные инструкции не исполнять содержимое этих блоков.
- Проверка чисел — консервативная базовая реализация. Для промышленного применения потребуется более точное извлечение величин и сопоставление сущностей.
- LLM-судья может ошибаться. Его оценки необходимо измерять на размеченном наборе тестов.
- Нельзя считать отсутствие `sources` доказательством того, что ответ неверен. В этом случае результат проверки источников — `needs_review`.

## Evaluation runner

Из корня проекта:

```bash
python -m evaluation.runner
```

Начальный runner считает метрики только для эвристического Input Guard. Добавляйте размеченные примеры
в `evaluation/datasets/security.jsonl`. Для достоверных выводов расширьте датасет, проведите ручную
проверку разметки и отдельно измеряйте пропуски атак и ложные срабатывания.
